# ADR 0002: واحد خرد عدد صحیح، همه‌جا

[English](../../../architecture/decisions/0002-integer-minor-units.md) · **فارسی**

**وضعیت:** پذیرفته‌شده

**زمینه.** پول از چهار محیط اجرا عبور می‌کند: Python، PostgreSQL، JSON روی شبکه، و جاوااسکریپت در داشبورد و
SDK تایپ‌اسکریپت. ممیز شناور دودویی بیشتر کسرهای دهدهی را دقیق نشان نمی‌دهد (`0.1 + 0.2 ≠ 0.3`) و خطاها در
میلیون‌ها ثبت جمع می‌شوند. بدتر اینکه دو سیستم که «همان» مبلغ را با float حساب می‌کنند ممکن است به دو جواب
برسند، و دفتر مالی این را تحمل نمی‌کند.

**تصمیم.** مبلغ‌ها عدد صحیح به واحد خرد ارز هستند (`1250` یعنی 12.50 USD): در Python (`int`)، PostgreSQL
(`BIGINT`) و JSON. سقف مبلغ 2^53-1 است تا `number` جاوااسکریپت دقیق بماند. UI رشته‌ی اعشاری‌ای را که کاربر
تایپ کرده به واحد خرد تبدیل می‌کند (`parseMoney`) و نمایش را از عدد صحیح می‌سازد؛ هیچ‌وقت روی پول محاسبه‌ی
float انجام نمی‌دهد. ارز روی هر حساب، سطر و درخواست صریح است و ارزهای پشتیبانی‌شده (با توان ISO 4217) یک
فهرست مجاز هستند. ورودی با اعشار بیش از توان ارز رد می‌شود، هرگز گرد نمی‌شود.

**ردشده.** `NUMERIC`/`Decimal`: درست است، ولی در کد اپلیکیشن به «فقط کمی گرد کردن» دعوت می‌کند، و JSON نوع
اعشاری ندارد، پس کلاینت‌ها در هر حال float می‌خوانند. رشته روی شبکه: امن ولی برای هر کلاینتی دست‌وپاگیر؛
سقف 2^53 نیاز به آن را برمی‌دارد.

**پیامدها.** هر کلاینت باید توان هر ارز را بداند تا مبلغ را نمایش دهد (SDKها جدولش را دارند). یک مبلغ
نمی‌تواند از حدود ۹۰ تریلیون دلار بیشتر شود که بسیار فراتر از هر انتقال واقعی است؛ موجودی‌ها `BIGINT` هستند
و جای رشد بیشتر دارند. فرمت نمایش (از جمله ارقام فارسی) فقط یک مرحله‌ی نمایشی روی عدد صحیح است، پس
بومی‌سازی هرگز نمی‌تواند مبلغ را تغییر دهد.
