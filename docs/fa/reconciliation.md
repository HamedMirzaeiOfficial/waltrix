# تطبیق (Reconciliation)

[English](../reconciliation.md) · **فارسی**

تطبیق هر چیزی را که می‌تواند از دفتر روزنامه‌ی تغییرناپذیر از نو می‌سازد و با رکوردهای قابل تغییر (موجودی‌های
ذخیره‌شده، وضعیت تراکنش‌ها و رزروها) مقایسه می‌کند. در **یک تراکنش REPEATABLE READ و READ ONLY** اجرا می‌شود،
پس همه‌ی بررسی‌ها یک snapshot را می‌بینند، حتی وقتی پول در حال جابه‌جایی است.

از داشبورد (تطبیق ← اجرا)، از API (`POST /api/v1/reconciliation/runs` با مجوز `reconciliation:run`)، یا از CLI
برای همه‌ی سازمان‌ها (`waltrix reconcile`، که با خطا exit code غیرصفر می‌دهد و برای cron و هشدار مناسب است)
اجرایش کنید.

## بررسی‌ها

| بررسی | شدت | چه چیزی را پیدا می‌کند |
| --- | --- | --- |
| `unbalanced_entry` | خطا | سندی که در یک ارز بدهکار ≠ بستانکار دارد |
| `short_entry` | خطا | سندی با کمتر از دو سطر |
| `trial_balance` | خطا | بدهکار ≠ بستانکار ثبت‌شده در کل سازمان، به تفکیک ارز |
| `posted_balance_mismatch` | خطا | جمع‌های ثبت‌شده‌ی حساب ≠ جمع سطرهای ثبت‌شده |
| `pending_balance_mismatch` | خطا | جمع‌های pending حساب ≠ سندهای pending رزروهای فعال |
| `overdraft` | خطا | حساب محافظت‌شده با موجودی قابل استفاده‌ی منفی |
| `posted_without_entry` | خطا | تراکنش POSTED/REVERSED بدون سند ثبت‌شده |
| `failed_with_postings` | خطا | انتقال/واریز/برداشت FAILED که سند دارد |
| `reversal_total_mismatch` | خطا | `reversed_amount` ≠ جمع برگشت‌های ثبت‌شده‌اش |
| `hold_state_mismatch` | خطا | وضعیت رزرو و وضعیت تراکنشش ناسازگارند |
| `funding_vs_wallets` | خطا | دارایی تأمین شبیه‌سازی‌شده ≠ کل بدهی کیف پول‌ها |
| `overdue_hold` | هشدار | رزرو فعالی که از `expires_at` گذشته (worker انقضا عقب است) |

خطا اجرا را ناموفق می‌کند؛ هشدار گزارش می‌شود ولی نه.

## یک بررسی چطور نوشته می‌شود

هر بررسی یک کوئری SQL در `CHECKS` است (`packages/ledger-core/src/waltrix_core/services/reconciliation.py`) که
**ردیف‌هایی را که قانون را نقض می‌کنند** برمی‌گرداند. هیچ ردیفی یعنی بررسی موفق بوده. برای مثال:

```sql
-- unbalanced_entry: یک ردیف برای هر (سند، ارز) که سطرهایش همدیگر را خنثی نمی‌کنند
SELECT p.entry_id::text AS id, p.currency,
       sum(CASE WHEN p.direction='debit'  THEN p.amount ELSE 0 END) AS debits,
       sum(CASE WHEN p.direction='credit' THEN p.amount ELSE 0 END) AS credits
  FROM postings p WHERE p.org_id = :org
 GROUP BY p.entry_id, p.currency
HAVING sum(CASE WHEN p.direction='debit' THEN p.amount ELSE -p.amount END) <> 0
```

این شکل بررسی‌ها را از هم و از موتور مستقل نگه می‌دارد: هر کدام یک سؤال تازه از دفتر روزنامه است، نه استفاده‌ی
دوباره از همان کدی که دارد بررسی می‌شود. حداکثر ۵۰ ردیف ناقض برای هر بررسی به‌عنوان یافته ذخیره می‌شود
(`MAX_FINDINGS_PER_CHECK`)؛ عدد خلاصه همیشه تعداد کامل است.

## چرا یک snapshot

با READ COMMITTED هر کدام از دوازده کوئری لحظه‌ی خودش را می‌دید. انتقالی که بین دو کوئری commit شود، مثلاً
`posted_balance_mismatch` و `funding_vs_wallets` را با هم ناسازگار می‌کرد: یک هشدار کاذب در ترافیک عادی.
`REPEATABLE READ` یک snapshot را برای کل اجرا ثابت می‌کند و `READ ONLY` تضمین می‌کند خود تطبیق نتواند چیزی
بنویسد. بعد نتیجه در یک تراکنش نوشتنی کوتاه و جدا ذخیره می‌شود.

## یک اجرا چه چیزی ذخیره می‌کند

هر اجرا در `reconciliation_runs` ذخیره می‌شود با:

* `status` (`passed` یا `failed`) و `duration_ms`؛
* یک `summary`: تعداد هر بررسی، جمع خطاها و هشدارها، تراز آزمایشی به تفکیک ارز، و تعداد ردیف‌ها (سندها،
  سطرها، حساب‌ها، تراکنش‌ها)؛
* حداکثر ۵۰ `finding` برای هر بررسی، هر کدام با نام بررسی، شدت و ردیف ناقض به‌شکل JSON.

یک رویداد حسابرسی (`reconciliation.run`) نوشته می‌شود و gauge پرومتئوس `waltrix_reconciliation_last_errors`
تعداد خطای آخرین اجرا را برای هشدار در اختیار می‌گذارد.

خلاصه در یک ستون `JSONB` است که ترتیب کلیدها را حفظ نمی‌کند؛ برای همین داشبورد بررسی‌ها را با یک ترتیب ثابت
(`CHECK_LABELS`) نمایش می‌دهد (فصل ۱۴ راهنما، داستان ۸).

## زمان‌بندی و هشدار

| کجا | چطور | هشدار روی |
| --- | --- | --- |
| cron یا `worker` در compose | `waltrix reconcile` ساعتی یا شبانه | exit code غیرصفر |
| Prometheus | جمع‌آوری `/metrics` | `waltrix_reconciliation_last_errors > 0` |
| بعد از restore یا failover | `waltrix reconcile` قبل از باز کردن ترافیک | هر خطا |

هشدار `overdue_hold` معمولاً یعنی `waltrix expire-holds` به اندازه‌ی کافی اجرا نمی‌شود، نه اینکه پول غلط است.

## رسیدگی به یافته‌ها

1. هر خطا را یک حادثه بدانید. موجودی را با SQL «درست» نکنید؛ این کار تطبیق بعدی را می‌شکند.
2. علت را از جزئیات یافته (شناسه‌ها)، گزارش حسابرسی و correlation id در لاگ‌ها پیدا کنید.
3. پول را با برگشت یا سند دستی بین حساب‌های داخلی اصلاح کنید تا خود اصلاح هم ثبت شود. انحراف کش
   (`posted_balance_mismatch` با دفتر روزنامه‌ی درست) را با یک migration بازبینی‌شده که ستون‌ها را از سطرها
   از نو حساب می‌کند اصلاح کنید و بعد تطبیق را دوباره اجرا کنید.

### یک مثال کامل

یک اجرا با `posted_balance_mismatch` و `funding_vs_wallets` برای یک حساب کیف پول شکست می‌خورد:

1. یافته شناسه‌ی حساب، جمع‌های ذخیره‌شده و جمع‌های مشتق از سطرها را نشان می‌دهد. سمت دفتر روزنامه با
   `unbalanced_entry` و `trial_balance` (هر دو موفق) سازگار است، پس دفتر روزنامه درست است و **کش** منحرف شده.
2. گزارش حسابرسی و لاگ‌های دیتابیس حوالی زمان انحراف، یک `UPDATE` دستی SQL روی `accounts` را نشان می‌دهند.
3. اصلاح یک migration است که `posted_debits` و `posted_credits` آن حساب را از سطرهایش از نو حساب می‌کند و نفر
   دومی بازبینی‌اش می‌کند. خود پول جابه‌جا نمی‌شود، پس سندی لازم نیست.
4. یک اجرای تازه موفق است؛ یادداشت حادثه به هر دو اجرا لینک می‌دهد.

اگر به‌جای آن `unbalanced_entry` شکست خورده بود، خود دفتر روزنامه غلط بود. تا وقتی triggerهای تأخیری فعال‌اند
این باید غیرممکن باشد، پس اولین سؤال این است که چه کسی آن‌ها را غیرفعال کرده.

`tests/integration/test_ledger_invariants.py::test_10_reconciliation_detects_tampered_cache` یک موجودی
ذخیره‌شده را دستکاری می‌کند و ثابت می‌کند اجرا با بررسی‌های مورد انتظار شکست می‌خورد.
