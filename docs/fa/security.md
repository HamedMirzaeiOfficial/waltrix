# مدل امنیتی

[English](../security.md) · **فارسی**

Waltrix یک پروژه‌ی آموزشی و متن‌باز است. حسابرسی امنیتی مستقل **نشده** و هیچ ادعای انطباق با مقررات
(PCI DSS، SOC 2، مجوز بانکی) ندارد. کنترل‌های زیر همان کاری است که کد واقعاً انجام می‌دهد.

## جداسازی مستأجرها (tenancy)

* هر ردیف متعلق به مستأجر `org_id` دارد و هر کوئری سرویس با `org_id` انجام‌دهنده فیلتر می‌شود.
* سازمان و نقش انجام‌دهنده از سرور می‌آید: از ردیف API key، یا از عضویت کاربر در سازمانی که در
  `X-Waltrix-Organization` آمده (در هر درخواست بررسی می‌شود). به مالکیتی که کلاینت ادعا کند هرگز اعتماد نمی‌شود.
* منبع یک مستأجر دیگر `404 not_found` برمی‌گرداند، دقیقاً مثل یک UUID تصادفی (بدون «پیشگوی وجود»). شناسه‌ها
  UUIDv4 تصادفی‌اند، نه شماره‌ی پشت‌سرهم.
* کلیدهای خارجی ترکیبی `(id, org_id)` ارجاع بین مستأجرها را در سطح schema غیرممکن می‌کنند؛ مثلاً یک سطر سند
  حتی با SQL خام هم نمی‌تواند به حساب سازمان دیگری اشاره کند.

## احراز هویت

| اعتبارنامه | ذخیره | عمر | نکته |
| --- | --- | --- | --- |
| رمز عبور | scrypt (n=2^14، r=8، p=1، salt ۱۶ بایتی) | - | حداقل ۱۰ نویسه؛ برای ایمیل ناموجود هم scrypt روی یک hash ساختگی اجرا می‌شود (زمان‌بندی) و همان خطا برمی‌گردد |
| session | SHA-256 یک توکن ۲۵۶ بیتی | ۱۲ ساعت، قابل باطل کردن | httpOnly، `SameSite=Strict`، `Secure` در production، محدود به path |
| API key | SHA-256 یک راز ۲۵۶ بیتی + پیشوند عمومی | انقضای اختیاری | فقط یک بار نشان داده می‌شود؛ `last_used_at` ثبت می‌شود |

**CSRF.** نوشتن با کوکی، هدر `X-Requested-With: waltrix-web` را هم لازم دارد. مرورگر اجازه نمی‌دهد سایت دیگری
بدون preflight CORS هدر سفارشی بفرستد، و CORS فقط فهرست صریح `WALTRIX_CORS_ORIGINS` را قبول می‌کند (هرگز `*`
همراه با credentials؛ پیش‌فرض خالی یعنی فقط همان origin).

## مجوزها

بسته‌های نقش → مجوز در `permissions.py` هستند؛ کد مجوز را بررسی می‌کند، هرگز نام نقش را.

| مجوز | مالک | مدیر | اپراتور مالی | حسابرس | بیننده |
| --- | :-: | :-: | :-: | :-: | :-: |
| خواندن کیف پول / دفتر کل | ✓ | ✓ | ✓ | ✓ | ✓ |
| مدیریت کیف پول، انتقال، واریز و برداشت، برگشت | ✓ | ✓ | ✓ | | |
| خواندن تطبیق | ✓ | ✓ | ✓ | ✓ | |
| اجرای تطبیق، گزارش حسابرسی | ✓ | ✓ | | ✓ | |
| سند دستی، حساب‌های داخلی | ✓ | ✓ | | | |
| اعضا، کلیدهای API | ✓ | ✓ | | | |
| تنظیمات سازمان | ✓ | | | | |

API key فقط می‌تواند نقش اپراتور مالی، حسابرس یا بیننده داشته باشد، و endpointهای مدیریت کلید و عضو session
کاربر لازم دارند، پس کلید لورفته نمی‌تواند کلید تازه بسازد. اعضا نمی‌توانند نقشی بالاتر از نقش خودشان بدهند،
و آخرین مالک را نمی‌شود حذف یا تنزل داد (عضویت‌ها حین بررسی قفل می‌شوند).

## راهنمای چرخش API key

1. جایگزین را بسازید (`POST /api-keys/{id}/rotate` با `grace_hours` > 0 برای بدون قطعی).
2. راز تازه را در secret manager و سرویس‌هایتان مستقر کنید.
3. `last_used_at` کلید قدیمی را زیر نظر بگیرید؛ با پایان مهلت (یا با ۰ فوراً) از کار می‌افتد.
4. وقتی کسی که دسترسی داشته می‌رود، یا کلیدی در لاگ یا مخزن دیده می‌شود، فوراً بچرخانید.

## محافظت از ورودی و سوءاستفاده

* مدل‌های Pydantic با `extra="forbid"`، مبلغ `StrictInt` و محدودیت طول؛ اعتبارسنجی سمت سرور مرجع است (UI فقط
  برای راحتی اعتبارسنجی می‌کند).
* rate limit: به ازای هر اعتبارنامه (پیش‌فرض ۶۰۰ در دقیقه) و به ازای IP و ایمیل برای ورود و ثبت‌نام (۱۰ در
  دقیقه). داخل پروسه است: با چند replica، هر کدام پنجره‌ی خودش را دارد. `X-Forwarded-For` فقط به اندازه‌ی
  `WALTRIX_TRUSTED_PROXY_COUNT` hop مورد اعتماد پذیرفته می‌شود.
* هدرهای امنیتی روی هر پاسخ: `nosniff`، `X-Frame-Options: DENY`، `Referrer-Policy: no-referrer`،
  `Cache-Control: no-store`.

## رازها و لاگ

* هیچ رازی در مخزن نیست؛ پیکربندی با متغیرهای محیطی `WALTRIX_*` (فایل `.env` در gitignore است).
* لاگ‌ها خط‌های JSON با method، الگوی route، status، مدت و correlation id هستند: بدون body، هدر، توکن یا رمز.
  metadata حسابرسی از کلیدهایی مثل `password`، `secret`، `token` پاک می‌شود.
* خطاهای غیرمنتظره یک 500 عمومی برمی‌گردانند؛ جزئیات زیر correlation id در لاگ می‌ماند.

## سخت‌سازی دیتابیس (برای هر استقرار واقعی توصیه می‌شود)

* migrationها را با نقش مالک اجرا کنید؛ API را با نقشی اجرا کنید که فقط `SELECT, INSERT, UPDATE` روی جدول‌های
  لازم دارد و مالک آن‌ها **نیست** (پس نمی‌تواند `TRUNCATE` کند یا triggerها را غیرفعال کند).
* TLS تا PostgreSQL، backup رمزنگاری‌شده، دسترسی شبکه‌ای محدود.

## کمبودهای شناخته‌شده

MFA، SSO، فرایند بازیابی رمز، تأیید ایمیل، فهرست IP مجاز برای هر کلید و رمزنگاری در سطح فیلد وجود ندارد و
rate limiting در حافظه است. نقشه‌ی راه در README را ببینید.
