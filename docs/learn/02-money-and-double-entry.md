## ۱. چرا float برای پول ممنوع است

```python
>>> 0.1 + 0.2
0.30000000000000004
```

`float` عدد را در مبنای ۲ نگه می‌دارد و `0.1` در مبنای ۲ دقیق نمایش داده نمی‌شود. در یک دفتر مالی میلیون‌ها جمع انجام می‌شود و این خطاهای ریز جمع می‌شوند؛ مهم‌تر، دو سیستم که «همان» عدد را حساب می‌کنند ممکن است دو جواب متفاوت بدهند.

**راه‌حل Waltrix:** همه‌ی مبلغ‌ها **عدد صحیح به واحد خرد**اند: `1250` یعنی 12.50 USD. در پایتون `int`، در PostgreSQL `BIGINT`، در JSON عدد صحیح.

```python
def validate_amount(amount: object, *, field: str = "amount") -> int:
    if isinstance(amount, bool) or not isinstance(amount, int):
        raise ValidationFailed(...)
```

چرا `bool` جدا چک شده؟ چون در پایتون `True` یک `int` است (`isinstance(True, int) == True`). بدون این خط، `amount=True` یعنی یک سنت!

### سقف 2^53 − 1

جاوااسکریپت فقط `number` دارد (float 64 بیتی) که اعداد صحیح را فقط تا `Number.MAX_SAFE_INTEGER = 2^53 − 1` دقیق نگه می‌دارد. پس Waltrix مبلغ‌ها را به همین سقف محدود کرده (`MAX_AMOUNT`). نتیجه: داشبورد و SDK تایپ‌اسکریپت بدون `BigInt` و بدون رشته، دقیق کار می‌کنند. موجودی‌ها در `BIGINT` (تا 2^63) هستند، پس جای جمع‌شدن هست.

### ورودی کاربر: رشته، نه float

کاربر می‌نویسد `12.5`. اگر `Number("12.5") * 100` کنید، برای بعضی عددها به `1249.9999` می‌رسید. `packages/typescript-sdk/src/money.ts::parseMoney` روی **رشته** کار می‌کند: بخش صحیح و اعشار را جدا می‌کند، اعشار را تا توان ارز پر می‌کند و می‌چسباند: `"12" + "50" → 1250`. اگر کاربر بیشتر از توان ارز اعشار بنویسد (`12.345` دلار) ورودی رد می‌شود، **گرد نمی‌شود**.

**درس:** گرد کردن یک تصمیم کسب‌وکاری است، نه یک جزئیات پیاده‌سازی. اگر نمی‌دانید چطور گرد کنید، رد کنید.

## ۲. ارز همیشه صریح است

هر حساب دقیقاً یک ارز دارد. هر سطر سند ارز دارد. هر درخواست ارز دارد. فهرست ارزهای مجاز در `CURRENCY_EXPONENTS` است (JPY توان ۰، USD توان ۲). «هر سه حرفی قبول است» یعنی روزی کسی `USDT` یا `usd ` وارد می‌کند.

## ۳. حسابداری دوطرفه در یک صفحه

هر رویداد مالی دست‌کم **دو** حساب را تغییر می‌دهد و مجموع بدهکارها با مجموع بستانکارها برابر است. پول از هیچ ساخته نمی‌شود و ناپدید نمی‌شود؛ فقط جابه‌جا می‌شود.

| نوع حساب | سمت طبیعی | مثال در Waltrix |
| --- | --- | --- |
| دارایی (asset) | بدهکار | `system:simulated_funding`: پولی که از بیرون وارد شده |
| بدهی (liability) | بستانکار | **هر کیف پول**: چیزی که به مشتری بدهکاریم |
| سرمایه / درآمد | بستانکار | حساب‌های داخلی دستی |
| هزینه | بدهکار | حساب‌های داخلی دستی |

چرا کیف پول «بدهی» است؟ چون از دید ما (نگهدارنده‌ی پول)، موجودی مشتری چیزی است که به او **بدهکاریم**. وقتی مشتری پول واریز می‌کند، دارایی ما بالا می‌رود (بدهکار funding) و بدهی‌مان به او هم بالا می‌رود (بستانکار wallet).

```
واریز ۱۰۰ دلار:   Dr simulated_funding 10000   |   Cr wallet:alice 10000
انتقال ۳۰ دلار:   Dr wallet:alice       3000   |   Cr wallet:bob    3000
```

### یک ناوردایی که از همین مدل می‌آید

چون پول فقط با واریز وارد و فقط با برداشت خارج می‌شود، برای هر ارز همیشه باید:

```
مانده‌ی بدهکار حساب funding  ==  مجموع بدهی به همه‌ی کیف پول‌ها
```

reconciliation دقیقاً همین را چک می‌کند (`funding_vs_wallets`). یعنی «پول از هیچ ساخته نشده» یک جمله‌ی شعاری نیست؛ یک کوئری SQL است.

## ۴. قوانین یک سند معتبر (`rules.validate_entry`)

1. دست‌کم دو سطر.
2. هر مبلغ عدد صحیح مثبت و زیر سقف.
3. **برای هر ارز جداگانه** بدهکار = بستانکار. یعنی `Dr 100 USD / Cr 100 EUR` رد می‌شود، با اینکه «۱۰۰ = ۱۰۰»! این همان «تبدیل ارز پنهان» است که صورت مسئله ممنوع کرده.
4. یک حساب در یک سند هم بدهکار و هم بستانکار نمی‌شود (این معمولاً نشانه‌ی باگ است).

## ۵. موجودی‌ها چطور ذخیره می‌شوند

به‌جای یک ستون `balance` که می‌تواند منفی و مثبت شود، هر حساب چهار جمع **نامنفی** دارد:

```
posted_debits, posted_credits, pending_debits, pending_credits
```

و موجودی از آن‌ها **مشتق** می‌شود (`rules.signed_balance`، `available_balance`):

```
موجودی ثبت‌شده (حساب بستانکار-طبیعی) = posted_credits − posted_debits
قابل برداشت                         = posted_credits − posted_debits − pending_debits
```

مزیت: هر ستون فقط بزرگ می‌شود (جز آزاد شدن هولد)، و می‌توانیم آن را مستقیم با جمع سطرهای سند مقایسه کنیم. توجه کنید که پولِ **در راهِ ورود** (pending_credits) در «قابل برداشت» حساب نمی‌شود.

## تمرین‌ها

1. در پایتون `sum([0.1] * 10) == 1.0` را امتحان کنید. بعد با `Decimal` و با عدد صحیح. نتیجه را توضیح دهید.
2. `parseMoney("0.07", "USD")` را با `Math.round(Number("0.07") * 100)` و `Number("0.07") * 100` مقایسه کنید. کدام ورودی‌ها روش دوم را می‌شکنند؟
3. سند «پرداخت کارمزد ۲ دلاری از کیف پول به حساب درآمد» را با جدول Dr/Cr بنویسید. آیا ناوردایی funding_vs_wallets هنوز برقرار است؟ (راهنمایی: نه! بعدش چه باید کرد؟)
4. چرا `available_balance` برای حساب‌های بدهکار-طبیعی `pending_credits` را کم می‌کند و نه `pending_debits`؟
