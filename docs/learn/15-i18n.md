# فصل ۱۵ — دوزبانه کردن داشبورد مالی

[English](en/15-i18n.md) · **فارسی**

## هدف این فصل

ببینید یک داشبورد مالی را چطور فارسی و انگلیسی کنیم بدون اینکه چیزی از «درستی پول» کم شود: متن، جهت راست‌به‌چپ، ارقام فارسی، تقویم شمسی، ورود مبلغ با ارقام فارسی، و یک ظرافت که فقط در نرم‌افزار مالی پیش می‌آید: تغییر زبان وسط یک عملیات نامعلوم.

فایل‌های اصلی:

| فایل | نقش |
| --- | --- |
| `apps/web/src/lib/i18n.ts` | `t()`، `msg()`، زبان فعلی، `intlLocale()`، تبدیل ارقام |
| `apps/web/src/lib/lang.tsx` | `LangProvider`، دکمه‌ی تغییر زبان، `useLanguageLock` |
| `apps/web/src/locales/fa.json` | دیکشنری فارسی (حدود ۴۷۰ رشته) |
| `apps/web/src/lib/format.ts` | پول، تاریخ، عدد و برچسب enumها بر اساس زبان |
| `apps/web/scripts/i18n-check.mjs` | بررسی CI: هیچ رشته‌ای بدون ترجمه نماند |
| `apps/web/index.html` | تعیین زبان و جهت **قبل** از بارگذاری React |

## متن انگلیسی خودش کلید است

```ts
t("Transfer posted");                       // "Transfer posted" یا «انتقال ثبت شد»
t("Available: {amount}", { amount: "$12" }); // جای‌گذاری؛ عددها در فارسی با ارقام فارسی
```

چرا کلیدی مثل `transfer.posted.title` نه؟

- کد خواناتر می‌ماند: متنی که در کد می‌بینید همان است که کاربر انگلیسی می‌بیند.
- اگر ترجمه‌ای جا بیفتد، کاربر فارسی یک جمله‌ی **خوانا** به انگلیسی می‌بیند، نه `transfer.posted.title`.
- بهای این انتخاب: اگر متن انگلیسی عوض شود، کلید هم عوض می‌شود. بررسی CI این را می‌گیرد (پایین‌تر).

### `msg()` برای جدول‌های ثابت

بعضی متن‌ها در **زمان بارگذاری ماژول** ساخته می‌شوند، مثل پیام‌های zod یا جدول پیام خطاها. آن موقع هنوز معلوم نیست زبان چیست (و ممکن است بعداً عوض شود). پس آن‌ها با `msg()` فقط **علامت** می‌خورند و در زمان نمایش ترجمه می‌شوند:

```ts
const MESSAGES = { insufficient_funds: msg("The source wallet does not have enough available balance.") };
// هنگام نمایش:
return t(MESSAGES[err.code]);
```

`tMaybe()` همین کار را برای خطاهای فرم انجام می‌دهد که ممکن است `undefined` باشند.

### خطاها با کد ترجمه می‌شوند، نه با متن سرور

`lib/errors.ts` پیام را از روی `err.code` (مثل `insufficient_funds`) انتخاب می‌کند. کدها بخشی از **قرارداد** API هستند و عوض نمی‌شوند؛ متن پیام سرور ممکن است عوض شود. پس API می‌تواند انگلیسی بماند و داشبورد پیام را به زبان کاربر نشان دهد. پیام‌های اعتبارسنجی فیلدها از API به انگلیسی می‌آیند و همان‌طور نمایش داده می‌شوند؛ این یک محدودیت آگاهانه است.

## enumها: `humanize()` ترجمه هم می‌کند

API مقدارهایی مثل `finance_operator` یا `posted` برمی‌گرداند. `humanize()` اول آن را به «Finance operator» تبدیل می‌کند، بعد `t()` را صدا می‌زند. مشکل: اسکریپت بررسی فقط **رشته‌های ثابت** داخل `t("...")` را می‌بیند، نه مقدارهایی که در زمان اجرا ساخته می‌شوند. راه‌حل، فهرست `ENUM_LABELS` در `format.ts` است: هر برچسب ممکن یک بار با `msg()` نوشته شده تا بررسی بداند باید ترجمه داشته باشد.

## زبان قبل از اولین رندر

اگر زبان را React تعیین کند، کاربر فارسی یک لحظه صفحه‌ی **چپ‌به‌راست** و انگلیسی می‌بیند و بعد صفحه برمی‌گردد. برای همین یک اسکریپت کوچک در `index.html`، قبل از بارگذاری React:

1. انتخاب ذخیره‌شده را از `localStorage` (`waltrix-lang`) می‌خواند؛
2. اگر نبود، از زبان مرورگر (`navigator.language` که با `fa` شروع شود)؛
3. `<html lang dir>` را تنظیم می‌کند.

`i18n.ts` در شروع همان `document.documentElement.lang` را می‌خواند. پس رندر اول از همان ابتدا درست است.

## تغییر زبان: remount زیر کش

`t()` یک تابع ساده است و هوک نیست، پس با عوض شدن زبان، کامپوننت‌ها خودبه‌خود دوباره رندر نمی‌شوند. حتی رندر دوباره‌ی ریشه هم کافی نیست: React وقتی شیء element یکسان باشد (مثل `<Outlet />` که بالاتر ساخته شده) از رندر زیرشاخه صرف‌نظر می‌کند.

پس `LangProvider` در `App.tsx` درخت را با `key={lang}` **از نو mount** می‌کند:

```tsx
<QueryClientProvider client={queryClient}>
  <LangProvider>   {/* key={lang} داخل این است */}
    …
```

چون `LangProvider` **زیر** `QueryClientProvider` است، کش داده‌ها می‌ماند و هیچ درخواستی دوباره فرستاده نمی‌شود. ولی state محلی کامپوننت‌ها از نو ساخته می‌شود. این به داستان ۱۱ فصل ۱۴ می‌رسد.

## قفل زبان: چیزی که فقط در نرم‌افزار مالی مهم است

اگر انتقالی در حال اجرا باشد یا نتیجه‌اش «نامعلوم» باشد، صفحه کلید idempotency را نگه داشته و خودکار بررسی می‌کند. remount یعنی آن state از دست برود و کاربر احتمالاً با کلید تازه دوباره بزند.

```ts
// TransferPage.tsx
useLanguageLock(isUnresolved(state));
// useIdempotentAction.ts (واریز، رزرو، برگشت)
useLanguageLock(status === "pending" || status === "unknown");
```

تا قفلی فعال است، `setLang` تغییر نمی‌دهد و یک toast توضیح می‌دهد. تست: `lib/lang.test.tsx`.

## راست‌به‌چپ (RTL)

### کلاس‌های منطقی

Tailwind 4 کلاس‌های منطقی دارد که با جهت عوض می‌شوند. کل کد از کلاس‌های فیزیکی به منطقی رفت:

| قبل (فیزیکی) | بعد (منطقی) |
| --- | --- |
| `text-left` / `text-right` | `text-start` / `text-end` |
| `pl-9`، `ml-2`، `-mr-2` | `ps-9`، `ms-2`، `-me-2` |
| `left-0`، `right-4` | `start-0`، `end-4` |
| `border-r`، `lg:pl-64` | `border-e`، `lg:ps-64` |

فلش‌های جهت‌دار (`ArrowLeft`، `ChevronRight`) با `rtl:-scale-x-100` آینه می‌شوند. آیکون‌های بی‌جهت دست نمی‌خورند. پنجره‌های وسط‌چین (`left-1/2 -translate-x-1/2`) هم دست نمی‌خورند.

### Radix و صفحه‌کلید

منوها، selectها و تب‌های Radix جهت‌یابی با صفحه‌کلید دارند (فلش چپ یعنی «قبلی»). `DirectionProvider` در `lang.tsx` جهت را به آن‌ها می‌دهد تا در فارسی فلش‌ها برعکس کار کنند.

### جزیره‌های چپ‌به‌راست

داستان ۱۰ فصل ۱۴ را ببینید. خلاصه:

- مبلغ در فارسی بین نویسه‌های LRI/PDI قرار می‌گیرد (`format.ts::ltr`) و `Money` با `dir="ltr"` رندر می‌شود، تا `‎-$10.00` هرگز `$10.00-` دیده نشود.
- شناسه‌ها و کدها (`.font-mono`) `unicode-bidi: isolate` دارند.
- نام‌هایی که کاربر وارد کرده `dir="auto"` می‌گیرند؛ ایمیل همیشه `dir="ltr"`.
- نمودار حجم عمداً `direction: ltr` می‌ماند: محور زمان در هر دو زبان از چپ به راست است، مثل بیشتر نرم‌افزارهای مالی فارسی.
- `th` به‌طور پیش‌فرض وسط‌چین است؛ در `index.css` به `text-align: start` تغییر کرد.

## عدد، پول و تاریخ با `Intl`

همه‌ی فرمت‌کننده‌ها `intlLocale()` را می‌گیرند: `fa-IR` یا `en-US`.

```ts
new Intl.NumberFormat("fa-IR").format(1234);                   // «۱٬۲۳۴»
new Intl.DateTimeFormat("fa-IR", { dateStyle: "medium" })      // «۲۸ آبان ۱۴۰۵»: تقویم شمسی خودکار
new Intl.RelativeTimeFormat("fa-IR").format(-6, "hour");        // «۶ ساعت پیش»
```

تقویم شمسی جدا پیاده نشده است؛ `fa-IR` در `Intl` به‌طور پیش‌فرض تقویم `persian` را دارد. فرمت‌کننده‌ها در هر فراخوانی ساخته می‌شوند (نه یک بار در بارگذاری ماژول)، چون زبان در زمان اجرا عوض می‌شود.

**یک قاعده‌ی مالی:** فرمت فقط برای **نمایش** است. `formatMoney` از SDK مبلغ را از عدد صحیح واحد خرد می‌سازد و فقط نمایش را به `Intl` می‌سپارد. هیچ مسیری از رشته‌ی فارسی به عدد float نیست.

## ورود مبلغ با ارقام فارسی

کاربر فارسی‌زبان ممکن است `۱۲٫۵۰` تایپ کند (ارقام فارسی و ممیز فارسی). `parseMoney` در SDK فقط ASCII را می‌پذیرد، و این درست است: SDK عمومی است و قرارداد ساده‌اش را حفظ می‌کند. داشبورد قبل از آن ارقام را تبدیل می‌کند:

```ts
toAsciiDigits("۱۲٫۵۰")        // "12.50"   (ارقام فارسی U+06F0..U+06F9، عربی U+0660..U+0669، ممیز ٫)
parseAmount("۱٬۰۰۰", "USD")   // 100000    (جداکننده‌ی هزارگان ٬ مثل ویرگول نادیده گرفته می‌شود)
```

`parseAmount` در `format.ts` جایگزین همه‌ی `parseMoney`های داشبورد شد. تست Playwright `e2e/i18n.spec.ts` یک انتقال واقعی با `۱۲٫۵۰` می‌زند و بعد در انگلیسی چک می‌کند موجودی دقیقاً `$87.50` شده باشد.

## فونت

Inter حروف فارسی ندارد. `@fontsource-variable/vazirmatn` اضافه شد. در انگلیسی Inter اول است و Vazirmatn فقط نویسه‌های فارسی را پوشش می‌دهد؛ در فارسی (`html[lang="fa"]`) Vazirmatn اول است تا متن فارسی و لاتین یک ریتم داشته باشند.

## بررسی خودکار در CI

```bash
npm run i18n:check -w @waltrix/web
```

`scripts/i18n-check.mjs`:

- همه‌ی `t("…")` و `msg("…")` با رشته‌ی ثابت را در `src/` پیدا می‌کند (با `"`، `'` یا backtick)؛
- اگر کلیدی در `fa.json` نباشد، **CI را می‌شکند**؛
- اگر مقداری در `fa.json` واقعاً فارسی نباشد، یا placeholderها (`{amount}`) در ترجمه با اصل نخوانند، خطا می‌دهد؛
- ورودی‌های بی‌استفاده را گزارش می‌کند؛
- با `--report` متن‌های JSX و ویژگی‌هایی مثل `placeholder="…"` را که در `t()` نیستند فهرست می‌کند؛
- با `--missing` کلیدهای بی‌ترجمه را به‌صورت JSON چاپ می‌کند تا ترجمه را شروع کنید.

یک باگ کوچک واقعی: Prettier دو کلید را که داخلشان `"` داشتند (`Revoke "{name}"?`) به رشته‌ی تک‌کوتیشن تبدیل کرد و اسکریپت، که اول فقط `"` را می‌شناخت، آن‌ها را «بی‌استفاده» گزارش داد. اسکریپت حالا هر سه نوع رشته را می‌شناسد.

## چه چیزی ترجمه نشده و چرا

| مورد | دلیل |
| --- | --- |
| پیام‌های API و متن خطای فیلدها | API برای توسعه‌دهنده است؛ کد خطا قرارداد ثابت است و UI با آن ترجمه می‌کند |
| نام کیف پول، توضیح تراکنش، نام سازمان | داده‌ی کاربر است، نه متن رابط |
| نام عمل‌ها در گزارش حسابرسی (`transfer.create`) | شناسه‌ی ماشینی است و برای جست‌وجو ثابت می‌ماند |
| کد ارز (`USD`) | استاندارد ISO 4217 است |

## تمرین

1. یک رشته‌ی تازه با `t("…")` به یک صفحه اضافه کنید و `npm run i18n:check -w @waltrix/web` را اجرا کنید. پیام خطا را بخوانید، ترجمه را اضافه کنید و دوباره اجرا کنید.
2. در `fa.json` یک placeholder را عمداً اشتباه بنویسید (`{amonut}`) و ببینید بررسی چه می‌گوید.
3. `rtl:-scale-x-100` را از دکمه‌ی «صفحه‌ی بعد» بردارید و در فارسی ببینید چرا لازم است.
4. چرا `LangProvider` باید **زیر** `QueryClientProvider` باشد و نه بالای آن؟ آن را جابه‌جا کنید و در تب Network مرورگر ببینید با تغییر زبان چه اتفاقی می‌افتد.
5. (سخت‌تر) به‌جای remount، زبان را با `useSyncExternalStore` به یک store تبدیل کنید و هر کامپوننتی که `t()` دارد subscribe کند. آیا هنوز به `useLanguageLock` نیاز دارید؟ چه چیزی سخت‌تر می‌شود؟
