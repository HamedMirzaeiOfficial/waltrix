# فصل ۵ — Idempotency: تکرار امن

فایل‌های این فصل: `services/idempotency.py`، `services/runner.py`، `apps/api/src/waltrix_api/deps.py::idempotency_key`، `packages/*-sdk`، [ADR 0004](../architecture/decisions/0004-idempotency-in-the-same-transaction.md)

## ۱. مسئله: «پاسخ نرسید»

کلاینت درخواست انتقال می‌فرستد. شبکه قطع می‌شود و پاسخی نمی‌رسد. آیا سرور پول را منتقل کرده؟ **نمی‌داند.**

- اگر دوباره بفرستد ← ممکن است دو بار پول منتقل شود.
- اگر نفرستد ← ممکن است انتقال انجام نشده باشد و مشتری منتظر بماند.

هیچ پروتکل شبکه‌ای «دقیقاً یک بار تحویل» را تضمین نمی‌کند. چیزی که می‌توانیم تضمین کنیم این است: **اجرای یک درخواست با یک کلید، حداکثر یک بار اثر دارد**، و کلاینت همیشه می‌تواند با تکرار، نتیجه را بفهمد.

## ۲. قواعد Waltrix

| قاعده | پیاده‌سازی |
| --- | --- |
| کلید در محدوده‌ی (سازمان، عملیات، کلید) | `UniqueConstraint("org_id", "operation", "key")` |
| اثر انگشت پارامترها | `fingerprint()`: SHA-256 از JSON مرتب‌شده |
| همان کلید + همان پارامتر ← نتیجه‌ی اصلی | replay با هدر `Idempotent-Replayed: true` |
| همان کلید + پارامتر دیگر ← تعارض | `409 idempotency_key_reused` |
| شکست کسب‌وکاری ذخیره و replay می‌شود | `outcome="failed"` + شناسه‌ی تراکنش FAILED |
| crash یا خطای غیرمنتظره ← کلید آزاد می‌ماند | چون کل تراکنش rollback می‌شود |
| در API اجباری | `Header(alias="Idempotency-Key")` بدون مقدار پیش‌فرض |

## ۳. ایده‌ی اصلی: رکورد idempotency در **همان** تراکنش

راه ساده‌لوحانه:

```
1. رکورد IN_PROGRESS بساز و commit کن
2. پول را منتقل کن و commit کن
3. رکورد را DONE کن و commit کن
```

بین هر مرحله ممکن است پروسه بمیرد: رکورد IN_PROGRESS یتیم می‌ماند (تا کی صبر کنیم؟)، یا پول منتقل شده ولی رکورد DONE نشده (retry دوباره منتقل می‌کند!). سه commit یعنی سه نقطه‌ی شکست.

راه Waltrix:

```python
with session.begin():
    record, stored = idempotency.claim(...)   # INSERT ... ON CONFLICT DO NOTHING
    ... انتقال پول ...
    idempotency.complete(record, ...)
# یک COMMIT
```

رکورد **اگر و فقط اگر** نتیجه‌ی مالی commit شده باشد وجود دارد. حالت «در جریان» هرگز بعد از commit دیده نمی‌شود، پس نیازی به timeout یا بازیابی رکوردهای یتیم نیست.

## ۴. درخواست‌های تکراری هم‌زمان

دو درخواست با یک کلید هم‌زمان می‌رسند. هر دو `INSERT ... ON CONFLICT DO NOTHING` می‌زنند. چه می‌شود؟

PostgreSQL برای حفظ unique index، `INSERT` دوم را **منتظر** نگه می‌دارد تا تراکنش اول تمام شود:

- اگر اولی commit کند ← `INSERT` دوم هیچ کاری نمی‌کند، `RETURNING` خالی است، ما رکورد commit شده را می‌خوانیم و replay می‌کنیم.
- اگر اولی rollback کند ← `INSERT` دوم موفق می‌شود و این درخواست «نویسنده‌ی اول» می‌شود.

یعنی بدون هیچ قفل دستی، خود unique index صف می‌سازد. تست `test_same_idempotency_key_concurrently_executes_once`: ۲۵ درخواست هم‌زمان، دقیقاً یک اجرا، ۲۴ replay، همه با همان شناسه.

## ۵. چرا شکست کسب‌وکاری ذخیره می‌شود؟

فرض کنید انتقال با `insufficient_funds` شکست خورد. بعد مشتری حساب را شارژ کرد و کلاینت همان درخواست را با **همان کلید** تکرار کرد. آیا باید موفق شود؟

Waltrix (مثل Stripe) می‌گوید **نه**: همان شکست قبلی برمی‌گردد. چون کلید یعنی «این همان درخواست است»، و آن درخواست قطعاً شکست خورده بود. اگر کاربر واقعاً «تلاش جدید» می‌خواهد، کلید جدید لازم است. این قاعده تست دارد: `test_6_business_failure_is_replayed_not_rerun`.

## ۶. سمت کلاینت: کلید یک بار ساخته می‌شود

در SDK پایتون (`_endpoints.py`):

```python
def create_transfer(..., idempotency_key: str | None = None) -> Spec[Transaction]:
    return Spec("POST", "/transfers", body, idempotency_key=_key(idempotency_key))
```

`_key` اگر کلیدی داده نشده باشد **یک بار** UUID می‌سازد؛ همه‌ی retryهای همان فراخوانی همان کلید را می‌فرستند. ولی بهتر است کلید از دامنه‌ی خودتان بیاید (`f"{order_id}:capture"`)، تا حتی بعد از restart پروسه هم یکسان بماند.

### سه نوع نتیجه، نه دو تا

| نتیجه | SDK پایتون | SDK تایپ‌اسکریپت |
| --- | --- | --- |
| موفق قطعی | مقدار برگشتی | مقدار برگشتی |
| شکست قطعی | `OperationFailedError` | `WaltrixApiError.isBusinessFailure` |
| **نامعلوم** | `UnknownOutcomeError(idempotency_key=...)` | `WaltrixUnknownOutcomeError` |

خطای «نامعلوم» مهم‌ترین طراحی SDK است. بیشتر کتابخانه‌ها timeout را مثل شکست گزارش می‌کنند و برنامه‌نویس فرض می‌کند «پول منتقل نشد». اینجا خطا صریحاً می‌گوید «شاید» و کلید را برای تکرار امن به شما می‌دهد. حتی لغو کاربر (`AbortSignal`) بعد از ارسال، برای mutation «نامعلوم» حساب می‌شود.

### کدام درخواست‌ها retry می‌شوند

فقط GETها و POSTهایی که کلید دارند، و فقط برای timeout، خطای اتصال، 429، 502/503/504 و `409 concurrent_request`. POST بدون کلید (مثل اجرای reconciliation) **هرگز** خودکار تکرار نمی‌شود. تست: `test_post_without_idempotency_key_is_never_retried`.

## تمرین‌ها

1. با `curl` یک انتقال بفرستید، بعد همان را دوباره بفرستید و هدر `Idempotent-Replayed` را ببینید. بعد مبلغ را عوض کنید. پاسخ چیست؟
2. در `claim` شرط `existing.fingerprint != fp` را بردارید. کدام تست می‌شکند؟ چه حمله یا باگی را این شرط جلوگیری می‌کند؟
3. طراحی کنید: اگر بخواهیم replay **عین بایت‌های پاسخ اول** را برگرداند (نه وضعیت فعلی)، چه چیزی باید ذخیره شود و چه هزینه‌ای دارد؟
4. چرا کلید idempotency باید در محدوده‌ی سازمان باشد؟ سناریویی بنویسید که بدون آن، یک مستأجر نتیجه‌ی مستأجر دیگر را ببیند.
