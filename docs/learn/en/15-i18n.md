# Chapter 15 — Making a financial dashboard bilingual

**English** · [فارسی](../15-i18n.md)

## Goal of this chapter

See how to make a financial dashboard Persian and English without weakening "correctness of money": text, right-to-left layout, Persian digits, the Solar Hijri calendar, entering amounts in Persian digits, and one subtlety that only comes up in financial software: switching language in the middle of an unknown operation.

The main files:

| File | Role |
| --- | --- |
| `apps/web/src/lib/i18n.ts` | `t()`, `msg()`, the current language, `intlLocale()`, digit conversion |
| `apps/web/src/lib/lang.tsx` | `LangProvider`, the language switch, `useLanguageLock` |
| `apps/web/src/locales/fa.json` | the Persian dictionary (about 470 strings) |
| `apps/web/src/lib/format.ts` | money, dates, numbers and enum labels by language |
| `apps/web/scripts/i18n-check.mjs` | the CI check: no string left untranslated |
| `apps/web/index.html` | sets language and direction **before** React loads |

## The English text is the key

```ts
t("Transfer posted");                       // "Transfer posted" or «انتقال ثبت شد»
t("Available: {amount}", { amount: "$12" }); // placeholders; numbers get Persian digits in Persian
```

Why not a key like `transfer.posted.title`?

- The code stays readable: the text you see in the code is what an English user sees.
- If a translation is missing, a Persian user sees a **readable** English sentence, not `transfer.posted.title`.
- The price of this choice: if the English text changes, the key changes. The CI check catches that (see below).

### `msg()` for constant tables

Some strings are built **when the module loads**, such as zod messages or the table of error messages. At that moment the language is not known yet (and it may change later). So they are only **marked** with `msg()` and translated when displayed:

```ts
const MESSAGES = { insufficient_funds: msg("The source wallet does not have enough available balance.") };
// when displayed:
return t(MESSAGES[err.code]);
```

`tMaybe()` does the same for form errors that may be `undefined`.

### Errors are translated by code, not by server text

`lib/errors.ts` picks the message from `err.code` (such as `insufficient_funds`). Codes are part of the API **contract** and do not change; the server's message text might. So the API can stay in English while the dashboard shows the message in the user's language. Field validation messages come from the API in English and are shown as they are; that is a deliberate limitation.

## Enums: `humanize()` translates too

The API returns values such as `finance_operator` or `posted`. `humanize()` first turns them into "Finance operator", then calls `t()`. The problem: the check script only sees **constant strings** inside `t("...")`, not values built at runtime. The answer is the `ENUM_LABELS` list in `format.ts`: every possible label is written once with `msg()` so the check knows it needs a translation.

## The language before the first render

If React decided the language, a Persian user would briefly see a **left-to-right** English page and then watch it flip. So a small script in `index.html`, before React loads:

1. reads the saved choice from `localStorage` (`waltrix-lang`);
2. otherwise uses the browser language (`navigator.language` starting with `fa`);
3. sets `<html lang dir>`.

At startup `i18n.ts` reads that same `document.documentElement.lang`. So the very first render is right.

## Switching language: a remount below the cache

`t()` is a plain function, not a hook, so components do not re-render on their own when the language changes. Even re-rendering the root is not enough: React skips a subtree when the element object is identical (like an `<Outlet />` created higher up).

So `LangProvider` in `App.tsx` **remounts** the tree with `key={lang}`:

```tsx
<QueryClientProvider client={queryClient}>
  <LangProvider>   {/* key={lang} is inside this */}
    …
```

Because `LangProvider` sits **below** `QueryClientProvider`, the data cache survives and no request is sent again. But components' local state is rebuilt. That leads to story 11 of chapter 14.

## The language lock: something that only matters in financial software

If a transfer is in flight or its outcome is "unknown", the page is holding the idempotency key and verifying automatically. A remount would lose that state, and the user would probably send again with a new key.

```ts
// TransferPage.tsx
useLanguageLock(isUnresolved(state));
// useIdempotentAction.ts (funding, holds, reversals)
useLanguageLock(status === "pending" || status === "unknown");
```

While any lock is active, `setLang` does not switch and a toast explains why. Test: `lib/lang.test.tsx`.

## Right-to-left (RTL)

### Logical classes

Tailwind 4 has logical classes that follow the direction. The whole codebase moved from physical to logical classes:

| Before (physical) | After (logical) |
| --- | --- |
| `text-left` / `text-right` | `text-start` / `text-end` |
| `pl-9`, `ml-2`, `-mr-2` | `ps-9`, `ms-2`, `-me-2` |
| `left-0`, `right-4` | `start-0`, `end-4` |
| `border-r`, `lg:pl-64` | `border-e`, `lg:ps-64` |

Directional arrows (`ArrowLeft`, `ChevronRight`) are mirrored with `rtl:-scale-x-100`. Icons without a direction are left alone. Centred dialogs (`left-1/2 -translate-x-1/2`) are left alone too.

### Radix and the keyboard

Radix menus, selects and tabs have keyboard navigation (left arrow means "previous"). `DirectionProvider` in `lang.tsx` gives them the direction so the arrows work the other way in Persian.

### Left-to-right islands

See story 10 of chapter 14. In short:

- In Persian, an amount is wrapped in LRI/PDI characters (`format.ts::ltr`) and `Money` renders with `dir="ltr"`, so `‎-$10.00` is never shown as `$10.00-`.
- Ids and codes (`.font-mono`) get `unicode-bidi: isolate`.
- User-entered names get `dir="auto"`; an email is always `dir="ltr"`.
- The volume chart deliberately stays `direction: ltr`: the time axis runs left to right in both languages, as in most Persian financial software.
- `th` is centred by default; `index.css` changes it to `text-align: start`.

## Numbers, money and dates with `Intl`

Every formatter takes `intlLocale()`: `fa-IR` or `en-US`.

```ts
new Intl.NumberFormat("fa-IR").format(1234);                   // "۱٬۲۳۴"
new Intl.DateTimeFormat("fa-IR", { dateStyle: "medium" })      // "۲۸ آبان ۱۴۰۵": the Solar Hijri calendar, automatically
new Intl.RelativeTimeFormat("fa-IR").format(-6, "hour");        // "۶ ساعت پیش"
```

The Solar Hijri calendar is not implemented separately; `fa-IR` in `Intl` uses the `persian` calendar by default. Formatters are created on every call (not once at module load), because the language changes at runtime.

**A financial rule:** formatting is for **display** only. The SDK's `formatMoney` builds the amount from the integer minor units and only delegates the display to `Intl`. There is no path from a Persian string to a float.

## Entering amounts in Persian digits

A Persian-speaking user may type `۱۲٫۵۰` (Persian digits and the Persian decimal separator). The SDK's `parseMoney` only accepts ASCII, and that is right: the SDK is public and keeps its simple contract. The dashboard converts the digits first:

```ts
toAsciiDigits("۱۲٫۵۰")        // "12.50"   (Persian digits U+06F0..U+06F9, Arabic-Indic U+0660..U+0669, the separator ٫)
parseAmount("۱٬۰۰۰", "USD")   // 100000    (the thousands separator ٬ is ignored, like a comma)
```

`parseAmount` in `format.ts` replaced every `parseMoney` in the dashboard. The Playwright test `e2e/i18n.spec.ts` makes a real transfer with `۱۲٫۵۰`, then checks in English that the balance is exactly `$87.50`.

## The font

Inter has no Persian glyphs. `@fontsource-variable/vazirmatn` was added. In English Inter comes first and Vazirmatn only covers the Persian characters; in Persian (`html[lang="fa"]`) Vazirmatn comes first so that Persian and Latin text share one rhythm.

## The automatic check in CI

```bash
npm run i18n:check -w @waltrix/web
```

`scripts/i18n-check.mjs`:

- finds every `t("…")` and `msg("…")` with a constant string in `src/` (with `"`, `'` or a backtick);
- **fails CI** if a key is missing from `fa.json`;
- fails if a value in `fa.json` is not actually Persian, or if the placeholders (`{amount}`) in the translation do not match the original;
- reports unused entries;
- with `--report`, lists JSX text and attributes such as `placeholder="…"` that are not wrapped in `t()`;
- with `--missing`, prints the untranslated keys as JSON so you can start a translation.

A small real bug: Prettier turned two keys that contain `"` (`Revoke "{name}"?`) into single-quoted strings, and the script, which at first only knew `"`, reported them as "unused". The script now recognises all three kinds of string.

## What is not translated, and why

| Item | Reason |
| --- | --- |
| API messages and field error text | the API is for developers; the error code is the stable contract and the UI translates by it |
| Wallet names, transaction descriptions, organization names | user data, not interface text |
| Action names in the audit log (`transfer.create`) | machine identifiers that stay fixed for searching |
| Currency codes (`USD`) | the ISO 4217 standard |

## Exercises

1. Add a new string with `t("…")` to a page and run `npm run i18n:check -w @waltrix/web`. Read the error, add the translation and run it again.
2. Misspell a placeholder in `fa.json` on purpose (`{amonut}`) and see what the check says.
3. Remove `rtl:-scale-x-100` from the "next page" button and look at it in Persian to see why it is needed.
4. Why must `LangProvider` be **below** `QueryClientProvider` and not above it? Swap them and watch the browser's Network tab when you switch language.
5. (Harder) Instead of a remount, turn the language into a store with `useSyncExternalStore`, and make every component that calls `t()` subscribe. Do you still need `useLanguageLock`? What becomes harder?
