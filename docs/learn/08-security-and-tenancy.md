# فصل ۸ — امنیت و چندمستأجری

فایل‌های این فصل: `apps/api/src/waltrix_api/deps.py`، `services/identity.py`، `permissions.py`، `services/queries.py`، `apps/api/tests/test_api.py`، [security.md](../security.md)

## ۱. قانون طلایی: به هویتی که کلاینت می‌گوید اعتماد نکن

کلاینت داشبورد هدر `X-Waltrix-Organization: <id>` می‌فرستد. اگر سرور همین را قبول کند، هر کاربری می‌تواند id سازمان دیگری را بنویسد. در `deps.py::current_actor`:

```python
actor = identity.actor_for_user(db, creds.user, org_id, correlation_id(request))
```

`actor_for_user` عضویت کاربر را **از دیتابیس** پیدا می‌کند و نقش را هم از همان‌جا می‌خواند. هدر فقط «انتخاب» است، نه «ادعای مجوز». برای API key، هدر سازمان کاملاً نادیده گرفته می‌شود چون کلید خودش به یک سازمان گره خورده (`test_api_key_is_bound_to_its_org`).

## ۲. جداسازی داده در سه سطح

1. **کوئری:** هر تابع در `queries.py` و `operations.py` با `org_id == actor.org_id` فیلتر می‌کند.
2. **schema:** FK ترکیبی `(id, org_id)` (فصل ۳).
3. **پاسخ:** منبع سازمان دیگر همان پاسخ «پیدا نشد» را می‌گیرد که یک UUID تصادفی.

سومی مهم است: اگر برای منبع دیگران `403` و برای ناموجود `404` بدهید، مهاجم می‌تواند با امتحان idها بفهمد کدام وجود دارد (**enumeration**). تست `test_cross_tenant_access_is_404` کد و پیام هر دو حالت را مقایسه می‌کند. idها هم UUID تصادفی‌اند، نه عدد پشت‌سرهم.

## ۳. نقش‌ها و مجوزها

```python
class Permission(StrEnum):
    MONEY_MOVE = "money:move"
    AUDIT_READ = "audit:read"
    ...
ROLE_PERMISSIONS = {Role.OWNER: frozenset(Permission), Role.VIEWER: frozenset(_READ), ...}
```

کد هیچ‌جا `if role == "admin"` نمی‌نویسد؛ همیشه `actor.require(Permission.MONEY_MOVE)`. نقش‌ها فقط بسته‌ای از مجوزها هستند و می‌شود بدون دست زدن به کد، آن‌ها را تغییر داد.

چک مجوز **داخل هسته** است، نه فقط در API. یعنی یک اپلیکیشن میزبان که مستقیم `operations.transfer` را صدا می‌زند هم نمی‌تواند با `Actor` نقش viewer پول جابه‌جا کند (`test_8_permissions_enforced_in_engine`).

### جلوگیری از ارتقای دسترسی

- هیچ‌کس نمی‌تواند نقشی بالاتر از نقش خودش بدهد (`ROLE_RANK`).
- آخرین owner را نمی‌شود حذف یا تنزل داد؛ و برای اینکه این چک در همزمانی هم درست باشد، همه‌ی عضویت‌های سازمان قفل می‌شوند (`_lock_membership`). بدون قفل، دو owner می‌توانستند هم‌زمان همدیگر را تنزل دهند و سازمان بی‌صاحب شود.
- API key فقط نقش‌های finance_operator، auditor یا viewer می‌گیرد و endpointهای مدیریت کلید و عضو session کاربر می‌خواهند. پس کلید لو رفته نمی‌تواند کلید جدید بسازد.

## ۴. رمز، session و API key

| | ذخیره | چرا |
| --- | --- | --- |
| رمز عبور | scrypt با salt تصادفی | کند است عمداً؛ رمزها آنتروپی کمی دارند |
| توکن session | SHA-256 | توکن ۲۵۶ بیت آنتروپی دارد؛ hash کند چیزی اضافه نمی‌کند |
| API key | SHA-256 + پیشوند عمومی | پیشوند برای نمایش در UI و لاگ، راز فقط یک بار نشان داده می‌شود |

**زمان‌بندی ورود:** اگر ایمیل وجود نداشته باشد و سرور فوراً جواب دهد، ولی برای ایمیل موجود scrypt اجرا کند (کند)، مهاجم از **زمان پاسخ** می‌فهمد کدام ایمیل ثبت شده. `login` برای ایمیل ناموجود هم scrypt را روی یک hash ساختگی اجرا می‌کند و پیام خطا در هر دو حالت یکی است (`test_login_failure_is_generic`).

## ۵. CSRF با کوکی SameSite و هدر سفارشی

داشبورد با کوکی httpOnly احراز هویت می‌شود (جاوااسکریپت به توکن دسترسی ندارد، پس XSS نمی‌تواند آن را بدزدد). خطر کوکی، CSRF است: سایت دیگری فرمی بسازد که به API ما POST کند و مرورگر کوکی را خودکار بفرستد. دو دفاع:

1. `SameSite=Strict`: مرورگر کوکی را در درخواست‌های بین‌سایتی نمی‌فرستد.
2. برای نوشتن با کوکی، هدر `X-Requested-With: waltrix-web` لازم است. مرورگر اجازه نمی‌دهد سایت دیگری هدر سفارشی بفرستد مگر بعد از preflight CORS، و CORS ما فقط originهای صریح را قبول می‌کند (پیش‌فرض: هیچ‌کدام).

## ۶. چیزهای کوچکی که مهم‌اند

- `extra="forbid"` در Pydantic: فیلد `balance` در درخواست ساخت کیف پول رد می‌شود (`test_unknown_fields_rejected`).
- `StrictInt` برای مبلغ: `"100"` و `true` و `10.5` همه ۴۲۲.
- rate limit جدا برای ورود (به ازای IP و ایمیل).
- `X-Forwarded-For` فقط به اندازه‌ی `TRUSTED_PROXY_COUNT` قابل اعتماد است؛ وگرنه هر کسی می‌تواند IP جعلی بنویسد و از rate limit فرار کند.
- لاگ‌ها body و هدر را ثبت نمی‌کنند؛ مسیر route به‌شکل الگو (`/wallets/{wallet_id}`) ثبت می‌شود، نه id واقعی.

## ۷. چیزی که ادعا نمی‌کنیم

MFA، SSO، بازیابی رمز و تأیید ایمیل وجود ندارد و پروژه حسابرسی امنیتی مستقل نشده. نوشتن صادقانه‌ی «چه چیزی نیست» بخشی از مستندات امنیتی است.

## تمرین‌ها

1. با یک API key از سازمان A، با `curl` سعی کنید کیف پول سازمان B را بخوانید و به آن انتقال بدهید. هدر `X-Waltrix-Organization` را هم بفرستید. نتیجه را توضیح دهید.
2. خط بررسی `X-Requested-With` در `deps.py` را موقتاً حذف کنید. کدام تست می‌شکند؟ یک صفحه‌ی HTML ساده بنویسید که حمله‌ی CSRF را نشان دهد (و بعد خط را برگردانید).
3. زمان پاسخ `/auth/login` را برای ایمیل موجود و ناموجود ۲۰ بار اندازه بگیرید. آیا تفاوت معناداری هست؟ بعد `_DUMMY_HASH` را حذف کنید و دوباره اندازه بگیرید.
